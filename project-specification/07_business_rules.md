# 07. Business Rules

> All the business logic extracted from the code — the rules that govern reservations, cancellations, notifications, statuses, permissions, time restrictions and priorities. Each rule notes where it lives.

---

## 1. Authentication & session rules

1. **Resident vs staff is decided by `tUserM.UserKbn`.** Resident logins (`login.php`→`login_finish.php`) require `UserKbn = '4'`; staff logins (`login_form.php`→`login_finish2.php`) require `UserKbn <> '4'`. (`httpdocs/login_finish.php`, `login_finish2.php`)
2. **Residents log in with property + room + password.** The match is on `BukkenCD` + `ID` (room number) + (`Passwd` or changed `Passwd2`) + `MukouFlg=FALSE` + `UserKbn='4'`. If a block (`editBuildingCD`) is given it must also match.
3. **Wrong password and unknown user show the same message** (`該当するユーザが見つかりませんでした。`) on purpose, to avoid revealing which part was wrong. (Internally there is a subtle wording difference "は" vs "が".)
4. **Email two-factor is mandatory** for residents whose email is verified, and for staff — *except* staff whose login ID contains `nespe` or who have `Skip2faFlg=1`, who bypass it. (`login_finish2.php` lines ~121)
5. **The 2FA code is 6 digits, expires in 30 minutes**, single-use, and is regenerated on "resend". (`login_finish.php`/`_finish2.php`)
6. **Unverified email forces a registration detour:** if `EmailVerified=0`, the resident must register & verify an email (`mail_regist.php`) before continuing.
7. **Session token `rKey`** identifies the user on every page and is rotated on login. **Idle timeout = 360 minutes**; after that the key is rotated and the user must re-login. (`SPFW/inc/global.inc` `$Timeout=360`; `SPUSUser::doAuthenticationByRegistKey`)

## 2. Property / building setup rules

1. **A property belongs to one Client (`ClientCD`)** and may be assigned to one equipment contractor (`GyosyaCD`) and one fire-prevention contractor (`GyosyaBousaiCD`).
2. **Multi-block properties** set `TatoFlg=1` and add `tBuildingM` rows; block-level dates/sizes override property-level when an `editBuildingCD` is in context.
3. **No-work days (`Holiday1`) and reserve days (`ReserveDay`)** are stored pipe-encoded and excluded from / reserved within the booking calendar.
4. **The slot grid is governed by:** `WakuPattern` (AM/PM slot layout from `$WAKUPATTERN`), `MaxWakuSu` (max slots per period, e.g. `10-10`), `Hansu` (parallel crews), `MinuteTime` (minutes per unit), `FirstDateFeature` (first-day restriction), `FrameOverflow` (allow overflow), and `FloorReserveInfo` (per-floor day/AM-PM/columns JSON).
5. **`ArrangeType`** distinguishes an inspection (点検, value 1) from a construction job (工事, value 0), which changes labels and some logic.
6. **New IDs are generated by lock + max+1**, not AUTO_INCREMENT — so two simultaneous inserts are serialized via `LOCK TABLE … WRITE`. (`SPUS*::executeUpdate`)
7. **Address is geocoded** (Google Maps) at first registration to store lat/lng. (`s_finish_sinki.php`)

## 3. Reservation rules

1. **One reservation per unit/room.** A unit's reservation is a `tReservationF` row with `Status=1`; the resident's answer state is on `tUserM` (`ReplyFlg`, `ConfirmFlg`).
2. **Slot availability** is computed live from the configured pattern minus existing bookings minus holidays. Calendar markers:
   - `○` 空きあり (available), `△` 残りわずか (few left), `×` 空きなし (full), `休` 休工日 (no-work day).
3. **A resident must complete their customer info** (name + phone) before they can book. Missing info redirects to `form.php`. (`reserve_form_kakutei.php`, `reserve_list.php`)
4. **First-day restriction (`FirstDateFeature`):** 1 = the morning of the first day is unavailable; 2 = the first day is unavailable until 15:00.
5. **Crew/lane assignment (`HanNo`)** is computed from capacity (`Hansu`/`MaxWakuSu`) when a slot is finalized.
6. **Double-submit protection:** the confirm/finish steps use a `$_SESSION['ticket']`; a stale/duplicate ticket is rejected.
7. **Reception window:** booking is only open between the property's start and `YoyakuEndDate`/`UketsukeShimekiriDate`. Outside it, the top screen shows `インターネットからの受付は終了しました。` and the booking button is hidden.
8. **`flag` on finish:** `1`=confirm new booking, `2`=change existing, `3`=decline.
9. **If no real open slot can be resolved at finish time**, the booking fails with an error and a link back to the top screen (prevents overbooking from a stale calendar).
10. **Reservation source is recorded:** `ReplyFlg=1` = booked via WEB, `2` = booked via TEL (staff `sh_list.php`).

## 4. Cancellation / decline rules

1. **Decline ("辞退")** sets `tUserM.ReplyFlg=3` and `ConfirmFlg=1` and shows `辞退で受付いたしました。次回のご協力よろしくお願いします。` (`kakutei.php` flag=3, `reserve_finish_kakutei.php`).
2. **A declined resident** can re-book later via `日程再予約` (the top button changes accordingly).
3. **Staff can "restore" (work=5)** a removed/declined booking from the phone-reception screen (`sh_list.php`).
4. **Deleting the schedule** (`doc/s_make_kanryo2.php` `work=2`) physically deletes all `tReservationF` rows for that property/block — destructive, intended for rebuilding the grid.

## 5. Completion rules

1. **A unit is "complete" when `tReservationF.KanryoFlg=1`.** This is set when a signature is saved (`s_sign_regist.php`) or by the completion-report download.
2. **A signature** is one `tSignF` row + a saved image file; deleting a signature (`s_kanryo.php` work=3 / `s_d2.php`) soft-deletes the row (`MukouFlg=1`) and reverts completion.
3. **The completion report** (`s_kanryo_download.php`) embeds every unit's signature image into `complete_report.xlsx` and marks `KanryoFlg=1`.
4. **`RefugeFlg=1`** marks a unit as absent/cannot-be-home; the crew/report treats it specially (no signature expected).

## 6. Status-change rules (the property lifecycle)

`tBukkenM.KikiStatus` (equipment) / `SougouStatus` (general) / `BousaiStatus` (fire-prevention) all use:

| Value | Meaning | Transition trigger |
|---|---|---|
| `0` | デフォルト (new / reset) | new property; or the +2-month request batch reset |
| `1` | 日程登録依頼済 (date-registration requested) | the request email batch (`s_MailIraiToSeko*`) or the per-property button (`IraiToSekoCompany.php`) |
| `2` | 日程入力済 (dates entered) | the date-entry/finish step |

- **The monthly request batch resets** matching properties to status 1 and clears the previous report (`ReportSubmitted=0`, old `tResultReportF` invalidated) — i.e. the cycle restarts each inspection period. (`s_MailIraiToSeko.php`)
- `ReportSubmitted=1` once the inspection result is submitted (`s_Result_Report_Finish.php`).
- The `STATUS` constant in `SPFW/inc/Tenken.properties` mirrors this: `デフォルト=0, 依頼済=1, 日程入力済=2`.

## 7. Notification rules (timing & recipients)

1. **Request to contractor:** fires for properties whose inspection month = **today + 2 months**. Resets status to 1 and emails the assigned contractor (`GyosyaMail`/`GyosyaMail2`). Only contractors with `IsSyoubou=1` (equipment) or `IsBouka=1` (fire-prevention) are targeted.
2. **Reminder to contractor:** same +2-month target, only if the property is still at status 0/1 (not yet registered). Subject prefixed `再通知`.
3. **Escalation to internal staff:** after ~16–20 days with no registration, emails the property's `TantoCD1..5` staff. Special CC rules exist (e.g. `ClientCD=131` Fukuoka CCs an extra address; a 16-day variant hardcodes a single overseer).
4. **Day-before reminder:** fires when `Date1` (equipment) or `BousaiStartDate` (fire-prevention) = **tomorrow** — sent to both the contractor and internal staff. (Filenames say "Yesterday" but the logic targets tomorrow.)
5. **Resident confirmation/change/decline emails** are sent immediately on the resident's action.
6. **Staff bell:** any resident booking/update writes `tBukkenWebActivityF`, lighting the header bell for staff scoped to that property.

(Full breakdown in **08_notification_specification.md**.)

## 8. Permission / scoping rules

1. **Staff (`UserKbn 1/2`) see only their own `ClientCD`'s properties and masters.**
2. **General staff (`UserKbn=1`, `UserType≠'1'`) are further limited to their `BrancheCD`** for the bell scope.
3. **Contractors (`UserKbn=3`) see only properties where `GyosyaCD` or `GyosyaBousaiCD` = their company.** New users they create get `ClientCD=0` and their own `GyosyaCD`.
4. **Master-data maintenance** is gated by `IfMasterMaintenance = (staff) AND (UserType='1')`.
5. **Residents (`UserKbn=4`) are excluded** from all staff lists (`AND UserKbn < 4`) and from the bell.
6. **IDs containing `nespe`** are treated as internal/developer accounts (skip 2FA; `IfNespe`).
7. **IP access gate (`common_accesscheck.php`):** internal VPN ranges (`192.168.97/98`) always pass; external IPs are blocked after 3 failed attempts in a day (`tOKIPM`). *(Used by some entry points.)*

(Full role table in **09_role_permission.md**.)

## 9. Time / date restrictions

- **Reception window:** start date → `YoyakuEndDate`/`UketsukeShimekiriDate`.
- **No-work days (`Holiday1`)** and **national holidays (`$SHUKUJITULIST` in 489.properties)** are excluded from bookable days.
- **Reserve days (`ReserveDay`)** are held back as buffer/overflow days.
- **First-day rule** (see §3.4).
- **Two-factor code expiry:** 30 minutes.
- **Session idle timeout:** 360 minutes.

---

## 10. Priority / ordering rules

- **Next-inspection month** on lists is the nearest of `KikiTenkenMonth`/`SougouTenkenMonth` to the current month (scanning current month +0..12).
- **Grid placement priority:** rooms fill slots by floor/`ViewOrderNo`/`HanNo`; `aki` (free) and `wakuover` (overflow) markers control overflow placement (`include/sh_list_slot_helpers.php`).
- **List pagination:** 20 rows/page on property lists; 10 default elsewhere (`SPFWListObject`).

---

## 11. Two inspection tracks (parallel rule sets)

- **消防点検 (fire-equipment):** `Kiki*` (機器, `TenkenKind=1`) and `Sougou*` (総合, `TenkenKind=2`) fields, `KikiStatus`/`SougouStatus`, equipment Excel templates `temp01–25.xlsx`, contractors with `IsSyoubou=1`.
- **防火/防災 (fire-prevention):** `Bousai*` fields, `BousaiStatus`, per-property Excel `template/bousai/<BukkenCD>.xlsx`, contractors with `IsBouka=1`, dedicated `*_bouka` screens and email scripts. Enabled per property by `BousaiFlg`.

---

## 12. Hidden / non-obvious rules worth flagging

- **`tUserM.Address1` holds the email address**, not the `EMail` column (which is marked unused). A developer reading the schema naïvely will look in the wrong column.
- **"Stylist" = inspection crew/班**, and "Menu" = the inspection service — both are vestigial names from SPFW's salon-booking origins.
- **A `tUserM` row often represents a *room*, not a person** (the resident login is per-unit).
- **Some batch scripts open a second DB connection to `kojikotei`** even though the configured main DB is `kojihochiki` — a likely-stale DSN (see **14_unknown_logic.md**).
- **2FA email sending is commented out in one helper** (`sendTwoFactorAuthMail` in `common_489.php`) but active inline in the login scripts — verify which path is live in your environment.
